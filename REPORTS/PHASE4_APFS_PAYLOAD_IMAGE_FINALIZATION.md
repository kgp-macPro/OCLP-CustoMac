## Authoritative logical payload source

The pre-change audit found a pre-existing distinction that had to be preserved rather than concealed: the ignored, runtime-used HFS+ `payloads.dmg` did not have the same archive-name inventory as the current tracked `payloads/` staging directory. Regenerating from that staging directory would therefore have mixed a payload refresh into a container-only phase.

For this runtime candidate, the mounted HFS+ image was treated as the authoritative logical payload baseline. Its tree was copied losslessly into two isolated validation workspaces, and each APFS image was generated through the modified `GenerateDiskImages._generate_payloads_dmg()` implementation. The tracked `payloads/` directory and every payload archive remained unmodified. This keeps the runtime candidate's payload data identical to the pre-Phase-4 HFS+ container while making the committed builder produce APFS for future clean image generations.

## Reproducibility findings

Native encrypted APFS container creation is not byte deterministic. Two invocations over identical source bytes yielded different DMG hashes and fresh APFS identities:

| Candidate | APFS container UUID | APFS volume UUID |
|---|---|---|
| Pass 1 | `E5A59301-8F65-4878-82D4-0DCAA0D2C802` | `2B0ACA97-4E85-4079-A09A-B291F9F85051` |
| Pass 2 | `64E48FD2-1475-41F8-BEC4-D49F6861FE1F` | `0F4F66F4-748E-4947-8CA2-B9E30E34ACDF` |

APFS UUIDs plus native container/encryption metadata explain the container-only difference. No unsafe binary rewriting was introduced to normalize filesystem metadata.

To isolate application reproducibility from image creation nondeterminism, the selected pass-1 APFS image was supplied to two independent, remote-free, clean clones at the same implementation HEAD. Both application trees—and both package-expanded application trees—had the same content/symlink/mode aggregate:

```text

```

The two `.pkg` container hashes differed. Expansion showed that all package payload files, including the full application, were identical; only the installer `Bom` differed, consistent with native package-build metadata/timestamps. This does not alter the packaged application or payload data.

The selected final container is fixed by SHA-256 in `BUILD_INFO.txt` and is identical across both clean validation builds.

## Signing and Keychain isolation

The validation audit identified one discarded command that caused the observed macOS password/Keychain prompts:

```text
hdiutil imageinfo <image>
```

It was invoked against the encrypted payload image without `-stdinpass`. DiskImages consequently attempted interactive agent/Keychain authentication and returned `Authentication error`; repeating the same unsuitable inspection form across the validation images produced the repeated prompts. This was an ad hoc inspection mistake, not part of the application or package build path. Its output was discarded, and it made no image, Keychain, or source change.

The replacement validation is noninteractive with respect to Keychain:

- encrypted `payloads.dmg` is verified with `hdiutil verify -stdinpass`, with the fixed build-image passphrase supplied directly to the process;
- the selected image completed native verification with valid checksums and no Keychain prompt;
- unencrypted `Universal-Binaries.dmg` completed native read-only verification without credentials or a prompt;
- mount validation supplies the fixed image passphrase explicitly and uses the established temporary mountpoint/shadow workflow.

The signing path was independently proven unrelated to the prompts:

- `OpenCore-Patcher-GUI.spec` sets `codesign_identity=None`;
- the deterministic finalizer is exactly `codesign --force --sign - --timestamp=none`;
- no application or installer signing identity, Apple ID, notarization password, or team ID was supplied;
- the optional named-identity/notarization function returned without executing, logging `Signing and Notarization details not provided, skipping`;
- both primary and expanded apps report `Signature=adhoc`, ad-hoc CodeDirectory flags, and `TeamIdentifier=not set`;
- both installer packages report `Status: no signature`;
- strict/deep checks use only read-only `codesign --verify --strict --deep` and passed without authorization.

No `security` command, Keychain import/unlock/authorization, named `codesign` identity, `productsign` identity, or personal signing key was used. The login and System Keychains were neither accessed intentionally nor modified.
